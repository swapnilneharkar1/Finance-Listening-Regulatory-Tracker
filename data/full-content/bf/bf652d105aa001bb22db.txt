Summary : IOTA changed materially when its Rebased mainnet went live on 5 May 2025. The current network uses a Move-based virtual machine, delegated proof of stake, validator and delegator economics, an object-centric ledger and fee-bearing transactions. That architecture is different from the earlier Stardust-era experience associated with Firefly. Ordinary token balances did not require a token swap merely because of the upgrade, but users still had to adopt supported wallet software and some complex legacy assets required a separate migration process. This article separates those operational questions from market-price narratives. It also explains, for an Indian reader, why custody records, acquisition cost, transfer history and tax deducted at source documentation matter independently of the protocol’s technology. The discussion is descriptive and based on official project documentation and current Indian tax materials; it is not an assessment of value, future adoption or suitability. Key Takeaways Show all 20 sections Advertisement (adsbygoogle = window.adsbygoogle || []).push({}); What the Rebased IOTA Network Actually Changed The project’s official launch material identifies 5 May 2025 as the Rebased mainnet activation date. Rebased replaced the Stardust protocol rather than adding a cosmetic wallet interface. Applications can now use the Move programming model, and on-chain assets are represented as objects with explicit ownership and programmable behaviour. Transactions consume gas and are finalised through the network’s proof-of-stake validator set. For researchers comparing old and current IOTA material, the date and protocol generation matter: an explanation of feeless Stardust transfers, Firefly-only workflows or the former coordinator model is not a current description of the Rebased network. MoveVM and the object model Move was designed around resources that cannot be copied or discarded accidentally. In IOTA’s implementation, coins, packages and other assets are represented as objects whose ownership and permitted state changes are enforced by the execution model. This can make asset provenance and application rules more explicit, but it does not eliminate smart-contract defects, unsafe wallet approvals, malicious packages or poor key management. A user should distinguish the security properties of the base protocol from the separate code, interface and operator risks of a decentralised application. Delegated proof of stake and epochs The official FAQ describes a delegated proof-of-stake system in which validators operate the network and IOTA holders may delegate stake. Rewards and validator performance are organised around epochs. Delegation does not transfer ownership of the delegated tokens to the validator, but it introduces operational choices: the selected validator can change performance, commission and status, reward timing is epoch-based, and protocol parameters can change through network governance. “Staking” therefore should not be presented as a fixed-interest deposit or guaranteed return. Token Utility, Fees and Supply Mechanics The IOTA token is used to pay gas, participate in staking and interact with applications on the network. Paying a transaction fee is distinct from the value moved: a wallet can display a transfer amount and a separate gas charge. Storage-related economics may also affect objects retained on chain. The project’s documentation discusses protocol issuance and reward mechanics, but any quoted percentage is parameter-dependent and is not a promised yield. Readers should verify current epoch parameters in the official explorer or wallet rather than carrying forward a historical annualised estimate. A protocol fee is also different from an exchange, broker or wallet-provider charge. An Indian purchaser may incur an INR deposit charge, spread, platform fee, withdrawal fee, network gas and tax withholding in the same economic journey. Good records identify each amount, the payer, the asset and the timestamp. Combining all deductions into one unexplained “fee” makes later reconciliation, cost-basis work and dispute handling unnecessarily difficult. Wallet Migration and Custody Controls Balances, keys and supported software The official upgrade guidance stated that holders did not need a token migration for ordinary balances and that the same private keys controlled the corresponding account on the new network. The practical change was the supported wallet environment: Firefly became a legacy application, while the current IOTA Wallet is designed for Rebased accounts. A seed phrase or private key should never be entered into a page reached through an unsolicited message, advertisement or search result. Users should obtain software from the project’s official documentation, verify the network and first test with a low-value transaction. Complex legacy assets Some Stardust-era NFTs and native-token structures do not map automatically to the Rebased object format. The project provides an official migration workflow for such assets. This is not the same as a public token swap. Before using a migration transaction, the holder should inventory the legacy objects, confirm which assets are supported, preserve transaction evidence and validate the receiving address. Unofficial “recovery agents” asking for a seed phrase or remote access are a separate fraud risk, not part of the protocol process. 1. Staking Workflow and Operational Limits Delegation is initiated through the official wallet by selecting a validator and an amount. Rewards accrue according to epoch rules and can be claimed or compounded only through supported transactions. A delegator remains exposed to token-price movement throughout the period. Validator commission reduces the delegator’s share; validator underperformance can reduce rewards; software and network changes can alter the workflow. The wallet may show an estimate, but an estimate is not a contractual return. Users also need sufficient liquid balance to pay gas for subsequent operations. What a staking record should contain For audit and tax review, retain the delegation transaction, validator identity, epoch, amount, reward receipts, dates and INR value methodology used in the books. The Indian tax character of a reward can depend on the facts, including how and when the taxpayer obtains dominion over it and whether the activity is investment or business-related. The later disposal of rewarded tokens is a separate event from initial receipt and may require a separately supportable acquisition value. The Act’s VDA transfer rules do not, by themselves, answer every income-recognition question for protocol rewards. Indian VDA Tax and TDS Recordkeeping IOTA is capable of falling within India’s statutory virtual digital asset definition. Under the current special regime, income from transfer of a VDA is taxed at 30 per cent, with applicable surcharge and cess. The deduction framework is restrictive: the cost of acquisition is generally the only deduction against transfer income, and a loss from transfer of a VDA cannot be set off against other income or carried forward. The transaction can also attract one per cent tax deduction at source on consideration under the current VDA withholding rule when its statutory conditions and thresholds are met. Platform withholding does not settle the final tax computation; the taxpayer must reconcile gross consideration, cost, withholding credit and return reporting. Transfers can include sale for rupees, exchange for another token and other disposals for consideration. A wallet-to-wallet movement between addresses beneficially owned by the same person is factually different, but it still requires evidence showing that ownership did not change. Gas paid in tokens, rewards, airdrops, wrapped assets and migration transactions can create valuation or character questions. The safest editorial conclusion is not to assume that every on-chain movement is taxable or tax-free. Classify the event from contracts, beneficial ownership and transaction data, then obtain advice for uncertain facts. Regulatory and tax risk: Indian reporting, withholding and valuation positions can change with law and facts. Frequently Asked Questions Did IOTA holders have to swap their tokens for Rebased? The official upgrade guidance said ordinary balances did not require a token swap. Holders needed compatible wallet access, while certain complex legacy assets required a dedicated migration workflow. Can Firefly be used for normal Rebased transactions? Firefly is treated as legacy software. The project directs Rebased users to the current IOTA Wallet and related official tools. Does delegation transfer my IOTA to a validator? Delegation assigns staking power under the protocol without transferring beneficial ownership to the validator, but the user remains responsible for validator selection and wallet security. Are staking rewards guaranteed? No. Rewards depend on protocol parameters, epoch participation, validator performance and commission; token value also fluctuates. Is every wallet movement a taxable VDA transfer in India? Not automatically. Beneficial ownership, consideration and transaction substance matter. Evidence is required to distinguish self-transfers, migrations and disposals. Can an IOTA transfer loss be set off against salary or share gains? The special VDA rule generally bars set-off and carry-forward of a loss from transfer of a VDA. Individual facts should be checked under the law applicable to the relevant year. Does exchange TDS finish the tax obligation? No. Withholding is a tax credit mechanism. Final income, cost and tax must still be computed and reported correctly. Key Takeaways The current IOTA network is the Rebased MoveVM network launched on 5 May 2025. Normal balances did not require a token swap, but current wallet software and some legacy-asset migrations require care. Staking is protocol participation, not a fixed-return deposit. Indian VDA transfer tax, TDS and recordkeeping apply independently of the technology narrative.
